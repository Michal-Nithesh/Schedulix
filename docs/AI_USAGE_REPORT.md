# AI Usage Report

## 1. AI Tool Used

**GitHub Copilot (coding assistant)**

GitHub Copilot was used throughout the development of Schedulix as a coding assistant for scaffolding, implementation support, code review, test generation, debugging, and documentation.

---

## 2. What I Asked AI to Do

The AI assistant was used for the following tasks:

1. Scaffold the full-stack project structure using React + Vite for the frontend, Express for the backend, and a Supabase-ready PostgreSQL schema.

2. Design and implement the timetable generation algorithm using recursive backtracking, most-constrained-first task ordering, hard constraints, soft constraints, and structured conflict reporting.

3. Design an independent timetable validation system capable of validating both automatically generated schedules and manually edited schedules.

4. Prepare realistic academic seed data containing departments, divisions, subjects, faculty, classrooms, time slots, availability, qualifications, and subject requirements.

5. Scaffold REST API routes, authentication, RBAC middleware, and CRUD operations for configuration entities.

6. Generate automated tests covering timetable generation, validation, conflict detection, backtracking, and authentication/RBAC.

7. Review implementation decisions, identify edge cases, debug incorrect behavior, improve validation, and prepare project documentation.

---

## 3. Prompt That Was Most Useful

> "Design an Intelligent Timetable Generator that schedules subjects, faculty, classrooms, divisions, and time slots while respecting hard constraints such as faculty conflicts, division conflicts, classroom conflicts, availability, room capacity, room type, and faculty qualification. Use recursive backtracking with constraint-aware candidate ordering and return the best partial timetable when a complete timetable cannot be generated. Explain the architecture, trade-offs, validation strategy, and edge cases."

This prompt helped structure the core scheduling approach.

It led to the following design decisions:

* Recursive backtracking instead of a purely greedy scheduler.
* Most-constrained-first ordering of scheduling tasks.
* Hard constraints being checked before candidate scoring.
* Soft constraints being used only to order valid candidates.
* Independent timetable validation.
* Structured conflict reasons for impossible schedules.
* Partial timetable handling when a complete schedule cannot be generated.

## 5. Code I Modified

AI-generated code was reviewed and modified to match the actual Schedulix requirements and database schema.

### Constraint logic

`isRoomEligible` and `getSubjectRequirement` were modified so that subject requirements can override the normal subject configuration.

The capacity requirement uses:

```text
max(division.studentCount, requiredSeats)
```

rather than relying only on the subject-level capacity.

### Backtracking state management

The initial `removeCandidate` implementation did not correctly rebuild period tracking after backtracking.

The state restoration logic was modified so that:

* division period tracking is restored;
* faculty period tracking is restored;
* soft-constraint scoring does not use stale state.

### Candidate scoring

The room-capacity scoring logic was corrected to consider the effective required capacity.

Faculty future-availability scoring was also corrected to account for both availability and current slot occupancy.

### Most-constrained-first ordering

`getStaticCandidateCount` was modified to correctly detect cases where:

* no qualified faculty exists;
* no suitable room exists.

This allows impossible tasks to be identified earlier.

### Seed data

Faculty qualifications, availability, and room capacities were adjusted so the normal demonstration configuration can generate a valid timetable while still providing data for conflict scenarios.

### Error handling

Database errors were mapped to meaningful HTTP responses.

For example:

* PostgreSQL `23505` → duplicate/conflict response.
* PostgreSQL `23503` → dependency/foreign-key response.

### Manual edit validation

Server-side validation was added to the timetable edit endpoint.

This ensures that the backend does not trust a client-side edit payload and persist an invalid timetable.

## 6. AI Output That Was Wrong

Several generated implementations required correction during development.

### Incorrect room feasibility

The initial generator did not correctly account for all room constraints, including capacity and room type.

### Incorrect test assumptions

Some generated test scenarios did not match the actual seed configuration.

For example:

* A 60-student division was assigned to a room with capacity 55.
* A faculty member was expected to teach a subject for which they were not qualified.

### Incorrect backtracking state restoration

The first implementation of `removeCandidate` removed the timetable entry but did not correctly rebuild the period-tracking maps.

This could leave stale soft-constraint information after backtracking.

### Incomplete capacity scoring

The initial scoring logic considered only division size and did not account for the `subject_requirements.required_seats` override.

### Client-only edit validation

The initial manual-edit implementation trusted the frontend payload without server-side re-validation.

## 10. Key Learning from AI-Assisted Development

AI significantly accelerated scaffolding and implementation, but generated code was treated as a starting point rather than as authoritative.

The final implementation was validated against:

1. The actual database schema.
2. The product requirements.
3. Automated tests.
4. Generated timetable behavior.
5. Manual browser workflows.
6. Authentication and authorization requirements.

This validation process was particularly important for the constraint engine because a scheduler can appear to work while still producing logically invalid timetables.
